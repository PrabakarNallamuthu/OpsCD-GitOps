# ADR-019: Immutability-First Data Model

| Field | Value |
|-------|-------|
| **Status** | Accepted |
| **Date** | 2026-08-11 |
| **Category** | Architecture |

## Context

SOX Section 802 requires that financial audit records be retained for 7 years and cannot be altered after creation. SOC 2 CC7.2 requires change management audit trails. GDPR Article 17 (right to erasure) creates a tension: some personal data in audit records must be erasable, while the records themselves must remain intact. The platform must resolve this tension without compromising audit trail integrity.

## Decision

Adopt an **immutability-first data model** for all audit records:
1. The `audit.records` table enforces append-only via PostgreSQL RLS (REVOKE UPDATE, DELETE from application role).
2. Every record includes a SHA-256 checksum over its content + the previous record's checksum (hash chain).
3. GDPR erasure is implemented via **cryptographic erasure**: PII fields are encrypted with a per-user Vault key; erasure = key deletion. The record structure remains intact; only the PII becomes irrecoverable.

## Alternatives Considered

### Option A: Soft-delete with audit flags
**Pros:** Simpler implementation; allows correction of erroneous records.
**Cons:** Records can still be mutated; does not satisfy SOX non-repudiation requirements; audit integrity depends solely on application-level enforcement.

### Option B: Event sourcing (append-only event log)
**Pros:** Natural fit for immutability; full audit trail as a first-class concern.
**Cons:** Higher operational complexity; projection rebuilds are expensive at scale; Kafka already provides the event log — a second event sourcing store adds redundancy without benefit.

## Consequences

**Positive:**
- Tamper detection via hash chain verification can be run on-demand by auditors.
- PostgreSQL-level enforcement means even a compromised application cannot alter records.
- GDPR and SOX requirements are simultaneously satisfied without compromising either.

**Negative:**
- Erroneous audit records cannot be deleted — a corrective record must be appended instead.
- Hash chain verification is O(n) and becomes expensive for >1M records; use sampling for large datasets.
- Cryptographic erasure means GDPR-erased record content is irrecoverable even by Opsera (by design).

## Compliance Impact

| Framework | Impact |
|-----------|--------|
| SOX       | Hash chain provides mathematical proof of record integrity (non-repudiation). |
| SOC 2     | CC6.1: cryptographic controls; CC7.2: immutable change management audit. |
| PCI-DSS   | Req 10.3: audit log protection from modification and destruction. |
| GDPR      | Art. 17: cryptographic erasure satisfies right to erasure without destroying audit records. |
| DORA      | Operational resilience: audit trail survives infrastructure failures due to hash chain verification. |
