# ADR-020: Event-Driven Decoupling via Kafka

| Field | Value |
|-------|-------|
| **Status** | Accepted |
| **Date** | 2026-08-11 |
| **Category** | Architecture |

## Context

The risk analysis pipeline involves: Release Service (creates release) → Risk Engine (analyzes) → Policy Engine (evaluates) → Audit Service (records) → Analytics Service (computes metrics). If these services communicate synchronously (REST/gRPC), a failure in any service blocks the entire pipeline. High-volume release events (target: 1000+ events/sec) would require synchronous horizontal scaling of all services simultaneously.

## Decision

Use **Apache Kafka via Strimzi** as the backbone for all inter-service communication. Services publish domain events to Kafka topics and consume asynchronously. Services are temporally decoupled — a downstream service outage does not block the upstream producer.

## Alternatives Considered

### Option A: Synchronous REST calls between services
**Pros:** Simpler debugging; no additional infrastructure; immediate consistency.
**Cons:** Cascading failures; tight coupling; all services must scale together; no replay capability; lost events on consumer failure.

### Option B: NATS JetStream
**Pros:** Lighter footprint than Kafka; built-in at-most-once and at-least-once semantics.
**Cons:** Less mature exactly-once semantics; smaller ecosystem; Strimzi provides superior Kubernetes-native management; no equivalent of Schema Registry for contract enforcement.

## Consequences

**Positive:**
- Risk Engine can process analyses at its own pace without blocking Release Service.
- Events can be replayed from any offset for debugging, backfilling, or disaster recovery.
- Schema Registry enforces backward-compatible event contracts, preventing breaking changes.
- Dead Letter Queues provide graceful degradation for processing failures.

**Negative:**
- Eventual consistency: the UI must handle the state where a release is created but analysis has not yet completed.
- Distributed transaction management requires care (Saga pattern for multi-step flows).
- Kafka adds operational overhead: broker management, consumer group monitoring, offset tracking.

## Compliance Impact

| Framework | Impact |
|-----------|--------|
| SOX       | Event replay capability enables audit trail reconstruction from Kafka history. |
| SOC 2     | CC9.1: event-driven architecture enables graceful degradation (availability). |
| PCI-DSS   | TLS/SASL-SCRAM on all Kafka connections (Req 4.2: encrypted transmission). |
| GDPR      | Kafka retention policy (7 days) limits personal data exposure in event payloads. |
| DORA      | Decoupling enables independent service deployments without full pipeline downtime. |
